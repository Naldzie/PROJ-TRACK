B1. THE PROBLEM
────────────────────────────────────────────────────────────────────────────

ProjectBaselineSchedule is frozen by design (audit trail of original plan).
But when a project receives extensions, the frozen baseline becomes stale
for "current pace" purposes — AI prediction, variance, and getProjectStatus()
all compare actual progress against a plan that no longer matches the real
timeline. The S-Curve chart's extension line also has no month-by-month
data to draw from, since project_extension only records the new deadline
date, not a recalculated month-by-month schedule.

Separately: the S-Curve "actual" line currently collapses to only the
LATEST progress record per month, losing multi-inspection dots (multiple
progress history records allowed per month). This is a related but
independent display bug.

Graph/S-Curve fixes are OUT OF SCOPE for this plan — mentioned only because
the two-column schema change below is what the chart will eventually consume.

B2. CHOSEN DIRECTION
────────────────────────────────────────────────────────────────────────────

Add ONE new column to project_baseline_schedule:
    original_planned_progress_percent  (decimal, nullable)

  - Existing planned_progress_percent becomes the "current effective plan"
    (gets adjusted/extended post-extension).
  - original_planned_progress_percent is frozen at initial setup, never
    touched again.
  - On initial setup: BOTH columns written with same value.
  - Post-extension new/edited rows: ONLY planned_progress_percent written;
    original_planned_progress_percent stays NULL (these months were never
    part of the original plan).
  - Backfill at migration time: set original_planned_progress_percent =
    current planned_progress_percent for all pre-existing rows.

This mirrors the existing projects table pattern:
  planned_end_date (live) vs original_planned_end_date (frozen) — same
  concept, already proven in this codebase.

Auto-redistribution of planned_progress_percent on extension approval:
  PLANNED — see adjusted_baseline_generation_plan.txt for full implementation.
  Reuses the existing Set Up Baseline modal in a new "adjust-baseline" mode:
  pre-populates all months, auto-generates extension months by stretching the
  original curve pattern, lets user review/edit, then bulk-saves (UPDATE existing
  + CREATE new + DELETE removed) in one transaction.

KEY DESIGN DECISION MADE (was an open question in B3.3/B3.4):
  How should the "strictly-increasing" rule work once extension_count > 0,
  given planned_progress_percent stays capped 0-100 (validation unchanged)?
  Resolved as: post-extension rows are compared ONLY against other
  post-extension rows (original_planned_progress_percent IS NULL) — NOT
  against the original frozen baseline's max. This lets the extension
  period run its own increasing sequence starting fresh, rather than
  requiring values to somehow exceed the original plan's 100%. Applied
  consistently in both storeBaselineSchedule() and updateBaselineSchedule().
  Flagged to the user as a judgment call in case original intent differs.

B8. SESSION LOG — July 1, 2026 (AI Model 2) — Set Up Baseline modal (B5 step 6)

CONTEXT: AI Model 1 built a first version of the Set Up Baseline modal while
the user waited on a token reset (files: _setup_baseline_modal.blade.php,
baseline-schedule-setup-modal.js). That version saved each month
immediately to the DB one at a time via the existing storeBaselineSchedule()
endpoint, and re-fetched the list via a GET route that was never registered.
AI Model 1 correctly diagnosed both problems before running out of tokens
but did not get to implement a fix. This session (AI Model 2) picked up
from that diagnosis and implemented the fix.

PROBLEMS FOUND (originally surfaced by user testing, diagnosed by AI Model 1):
  1. 404 on modal open: refreshSetupBaselineList() called
     GET /{role}/projects/{id}/baseline-schedules, but no GET route was ever
     registered for getBaselineScheduleMonths() (the existing blade renders
     months server-side via a normal Blade loop, so a JSON GET route was
     never needed before this modal).
  2. Partial-save integrity problem (user's own observation, confirmed
     correct): saving one month at a time meant an incomplete (< 100%)
     baseline could exist in the DB if the user cancelled partway through —
     wrong for a table whose whole design intent is "frozen original plan,
     write-once, immutable."

DESIGN DECISION MADE: rather than just registering the missing GET route
(which would have silenced the 404 but left problem #2 unresolved), redid
the modal to hold all months in local browser memory (setupLocalMonths
array) and only contact the server ONCE, on "Done — Lock Baseline," via a
new atomic bulk-insert endpoint. Nothing is written to the DB until the
full plan is valid and reaches 100%.

WHAT WAS BUILT:
  ✅ New method BaselineScheduleController::storeInitialBaselineSetup() —
     accepts the full `months` array in one request, validates as a whole
     (no duplicate months, strictly increasing %, final month = 100%,
     guards against re-running setup if a baseline already exists), and
     bulk-inserts inside a DB transaction — all months or none. Writes
     both planned_progress_percent AND original_planned_progress_percent
     identically (same as storeBaselineSchedule() does for
     extension_count == 0), freezing this as the permanent original plan.
  ✅ New routes (staff + admin): POST .../baseline-schedules/setup
     → storeInitialBaselineSetup().
  ✅ baseline-schedule-setup-modal.js — rewritten around local state:
     addSetupBaselineMonth() now pushes to a local array only (no network
     call); new removeSetupBaselineMonth() lets the user remove a
     mistakenly-added month before final submit (needed now that entries
     aren't independently saved/removable via the DB anymore);
     onSetupBaselineDone() is the ONLY function that talks to the server,
     submitting the whole local array at once.
  ✅ _setup_baseline_modal.blade.php — no changes needed; the list is
     fully JS-rendered into the existing container div.

BUGS FOUND AND FIXED DURING TESTING (July 1, 2026, this session):
  ✅ BUG #6: renderSetupMonthList()'s empty-state branch re-appended the
     ORIGINAL #setupMonthListEmpty placeholder node via getElementById().
     That node gets permanently destroyed the first time the container's
     innerHTML is overwritten with month rows, so returning to 0 months
     later (e.g. after removing the last/only month) threw
     "TypeError: appendChild parameter 1 is not of type 'Node'" —
     getElementById() returned null. Because the error was thrown mid-
     function, the subsequent updateSetupProgress() call in
     removeSetupBaselineMonth() never ran, leaving setupCurrentMaxPercent
     stuck at its pre-removal value — which is why re-adding a month
     afterward incorrectly compared against the OLD max (e.g. still
     blocked at "must be higher than 60%" even though the list was empty).
     One root cause, two symptoms. Fix: empty-state branch now writes the
     placeholder markup as an HTML string via innerHTML instead of
     depending on a DOM node reference that can be destroyed.
