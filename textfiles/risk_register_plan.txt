==============================================================================
  SECTION 3 — PROBLEM STATEMENT
==============================================================================

  The system currently only records what HAS happened (progress, issues) and
  auto-derives schedule-health badges (OVERDUE / AT RISK / risk levels). There
  is NO forward-looking, manually-maintained register of risks — things that
  COULD still go wrong — with a probability × impact score, mitigation plan,
  owner, and lifecycle status.

  Without it, the PMU cannot proactively track and retire risks; risk
  management is implicit in progress gaps rather than an explicit, auditable
  project artifact. The AI/regression module also has no risk data to factor
  into recommendations (future enhancement, see FLAGGED FOR FUTURE).

==============================================================================
  SECTION 4 — CHOSEN DIRECTION
==============================================================================

  Build a Risk Register as a first-class project-scoped entity that closely
  mirrors the existing Issues feature to stay consistent with codebase
  conventions:

  • New `risks` table + `Risk` model + `RiskFactory`.
  • Shared `RiskController` (App\Http\Controllers) used by all three role
    groups — admin/staff CRUD, contractor read-only.
  • UI lives INSIDE the existing Issues tab (renamed "Issues & Risks") with
    an All / Issues / Risks toggle. Tab DOM id stays "issues" so tab-switching,
    sessionStorage restore, and Overview cross-links keep working unchanged.
    Risk code stays in its own separate files (partial, modal, JS, CSS).
  • risk_score (1–9) and risk level (Low/Medium/High) computed automatically
    from probability × impact (Low=1, Medium=2, High=3).
  • ActivityLog on create/update/delete (audit trail, same as Issues).
  • High-level risks trigger an in-app notification to admins + the project's
    contractor (mirrors IssueReported); Low/Medium risks are visible only.
  • No attachments, no AI hook in this first build
    (see Decision Log + FLAGGED FOR FUTURE).

  Rationale: reuse the proven Issues patterns (routes, controller shape,
  modal-driven CRUD, lazy AJAX list, per-feature public/ assets, test
  conventions) minimizes risk and matches the project's development rules
  (Rule 7 — extend existing architecture, don't redesign).

==============================================================================
  SECTION 8 — DECISION LOG
==============================================================================

  Decision 1 — Risk Register is NOT redundant with existing risk labels
    Context: user asked whether the feature duplicates OVERDUE / AT RISK badges.
    Options considered: skip the feature; build it.
    Decision: build it. Existing labels are auto-computed, retrospective
      schedule-health indicators; the register is a manual, forward-looking,
      persistent risk artifact (probability × impact, mitigation, owner).
    Consequences: they are complementary — a risk that materializes becomes an
      Issue; the register is the "before", Issues the "after".

  Decision 2 — UI placement: same tab as Issues with a toggle
    Context: user asked to put risks in the same tab as Issues (separate code).
    Options considered: dedicated 6th tab; same tab two sections; same tab toggle.
    Decision: same tab, renamed "Issues & Risks", with All / Issues / Risks
      toggle. Tab DOM id stays "issues". Risk code files remain separate.
    Rationale: avoids tab bloat; matches Overview "Issues & Risks" card naming;
      keeps tab-switching/session/Overview cross-links untouched.
    Consequences: issues.blade.php gains a toggle bar and includes the risk
      partial; risk partial/modal/JS/CSS are independent files.

  Decision 3 — No AI/regression hook in the first build
    Context: user asked whether the regression/AI module can use this data.
    Options considered: build AI hook now; defer.
    Decision: defer. The Risk model gets clean scopes so AI services can adopt
      it later without redesign (see FLAGGED FOR FUTURE).
    Rationale: keeps scope tight; AI integration has no existing consumer yet.

  Decision 4 — Scoring model
    Context: how to compute risk score/level.
    Options considered: store manually entered score; compute from P × I.
    Decision: compute risk_score = probability × impact (Low=1, Med=2, High=3,
      range 1–9) at write time; level = 1–3 Low, 4–6 Medium, 7–9 High.
    Rationale: automatic, consistent, sortable; matches standard 3×3 risk matrix.

  Decision 5 — Permissions
    Context: who can manage risks.
    Decision: admin/staff create/update/delete; contractor read-only (mirrors
      Issues, consistent with the "contractors are read-only by design" rule).

  Decision 6 — Auditing
    Context: traceability requirement (dev Rule 11 / project norm).
    Decision: ActivityLog rows on create/update/delete
      ('Create Risk' / 'Update Risk' / 'Delete Risk').

  Decision 7 — Branching
    Context: project Rule 12.
    Decision: new branch phase-20-risk-register off main; merge to main only
      after user review/approval.

  Decision 8 — Scope exclusions (first build)
    Context: keep the feature focused.
    Decision: NO attachments, NO Excel/PDF export, NO overview-card widget this
      build. Notifications ARE included but LIMITED to High-level risks
      (see Decision 9).
    Consequences: attachments/exports/widget noted as FLAGGED FOR FUTURE;
      low-risk to add later on top of the same model/scopes.

  Decision 9 — Notification scope: High-level risks only
    Context: user asked whether all 3 roles should be "communicated" of risks
      and chose to be notified on High risks only.
    Options considered: visible-only (no notifications); notify on all new
      risks; notify on High risks only.
    Decision: in-app notification (RiskReported) to admins + the project's
      contractor ONLY when a risk with level High is created. Low/Medium risks
      remain visible-only. All 3 roles can always see the full list when they
      open the project (contractor read-only).
    Rationale: all-3-roles visibility is a core purpose; proactive alerts are
      reserved for the highest-priority risks to avoid notification noise.
    Consequences: RiskReported notification class + NotificationController
      render case + store() hook; notification tests in Phase 4.
