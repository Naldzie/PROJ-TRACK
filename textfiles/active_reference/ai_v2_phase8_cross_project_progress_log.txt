================================================================================
  1. PHASE SUMMARY
================================================================================

  Objective:
    When a project has insufficient progress observations for reliable
    regression, use completed projects of the same category to supplement
    or replace the prediction with aggregate historical data.

   Two Modes:
     • Supplement (0 observations):  No prediction — shows "Insufficient Data"
     • Supplement (1 observation):   Prepend synthetic points from similar
       completed projects to give regression enough context for a stable fit
     • Supplement (< ⅓ planned months):  Prepend synthetic points to real data

   Key Change During Implementation:
     HistoricalSimilarityService was originally optional (nullable) but during
     testing, Laravel's container would skip auto-resolution when a default
     `= null` was present. Changed to required dependency — the service has
     no dependencies of its own, so Laravel resolves it automatically.

   Status: ✅ IMPLEMENTED (all code and unit tests complete)

  Key Similarity Criteria:
    • category_id       30pts (mandatory — score is 0 if mismatched)
    • budget ±20%       25pts (normalized inverse deviation)
    • duration ±30%     20pts (normalized inverse deviation)
    • contractor_id     15pts (bonus — same contractor)
    • estimated_workers 10pts (if both non-null, ±40% tolerance)

  5. KEY DESIGN DECISIONS
================================================================================

   1. Required Dependency (changed from optional during implementation)
      HistoricalSimilarityService was originally injected as optional
      (?HistoricalSimilarityService = null). However, Laravel's service
      container uses the default value when a parameter is optional,
      so it never attempted to auto-resolve the service. Changed to
      a required dependency — since HistoricalSimilarityService has
      no constructor dependencies, Laravel resolves it automatically.

   2. Similarity Scoring
     Weighted additive model: each criterion contributes points up to its
     weight, and the score is normalized to 0-100. category_id is mandatory:
     if it doesn't match, score is 0 and the project is filtered out.

  3. Synthetic Point Scaling
     Rather than directly using aggregate curve values, the system
     computes the ratio between the first actual observation and the
     aggregate curve value at that relative position, then scales the
     entire aggregate to match the project's actual trajectory.

  4. Minimum Threshold
     The supplement threshold is max(ceil(plannedMonths/3), 2), ensuring
     that very short projects still get at least 2 observations before
     the system considers them "self-sufficient."

      Schedule-Aware, EAC_time) is not rendered. Suspected cause: the
      `completion_multi` data may not be passed through the presenter
      for supplement-mode predictions. Needs investigation.

   3. DB-Dependent Tests
      generateFallbackDataset and generateSupplementDataset require a live
      database. These are covered by the existing AIIntegrationTest
      framework. Consider adding dedicated integration tests with test
      factory data.

   4. Similarity Score Validation
      The similarity scoring weights (30/25/20/15/10) are initial estimates.
      Monitor real-world results and adjust weights if the system
      consistently selects poorly-matched projects.

   5. Production Monitoring
      After deployment, log data_source for each prediction to track how
      often fallback/supplement modes trigger. This data can guide weight
      tuning and threshold adjustments.


================================================================================
  8. PANEL Q&A NOTES (Potential Defense Questions)
================================================================================

  Q1: How did you determine the similarity weights (30/25/20/15/10)?

     A: Weights reflect relative importance for project progress patterns.
        Category is strongest (same type of work → similar S-curve shape),
        budget and duration define project scope, contractor and workers
        are refinements. This is a v1 heuristic — real data could tune
        these via regression or grid-search across historical projects.


  Q2: What if only 1-2 similar projects exist? Is the aggregate meaningful?

     A: Currently all matches are used. A MIN_SIMILAR_PROJECTS constant
        (e.g., 3) should be added — if fewer matched, fallback/supplement
        returns null and the system uses original data with a note.
        *Recommended before defense.*


  Q3: Why don't you weight newer projects higher (recency bias)?

     A: Valid point. All completed projects are treated equally regardless
        of age (e.g., 2018 vs 2025). A time-decay multiplier based on
        completion_date could be added. Limitation acknowledged.


  Q4: What if the target project's category has zero completed projects?

     A: findSimilarProjects returns empty → buildAggregateCurve returns
        empty → applyCrossProjectData skips → prediction proceeds using
        only the project's own data. The system degrades gracefully.


  Q5: What if the first observation is an outlier or very early (e.g., 0.5%)?

     A: The scaling ratio uses the first actual point. If it's near zero,
        the entire scaled curve becomes nearly flat. A ratio floor (e.g.,
        0.5) or averaging the first 2-3 observations would fix this.
        *Recommended before defense.*


  Q6: How do you know cross-project predictions are actually more accurate?

     A: This is v1 — effectiveness is not yet measured. The data_source
        field is logged per prediction, so post-deployment analysis can
        compare error rates of fallback/supplement vs actual-only data.


  Q7: Could PMU users misinterpret the cross-project disclaimer?

     A: The current disclaimer says "Based on X similar historical
        projects." This could be clarified to "Prediction supplemented
        by X similar past projects. Values are estimates, not guarantees."
        A tooltip icon next to the label adds further clarity.
