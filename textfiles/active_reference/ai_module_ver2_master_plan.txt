  ║ PHASE 1 — Polynomial Regression Engine (Core Math Upgrade)             ║
  ╚══════════════════════════════════════════════════════════════════════════╝

  Objective
  ---------
  Add polynomial (cubic) regression as an alternative to Simple Linear
  Regression. A degree-3 polynomial (y = ax³ + bx² + cx + d) can model
  S-curve shapes because it bends twice — slow start → rapid growth →
  plateauing completion.

  This is the FOUNDATION for most other V2 features. Without it, completion
  estimation and forecast tables would produce misleading results.

  Architecture
  ------------
  NEW:  app/Services/AI/Regression/PolynomialRegressionService.php

  Method: Least Squares via Gaussian Elimination
    • Set up normal equations for degree 3: Σx⁰ through Σx⁶
    • Solve 4×4 system using Gaussian elimination with partial pivoting
    • Return: a (x³), b (x²), c (x), d (intercept), R², fit quality

  Predict Equation:
    y = a(x³) + b(x²) + c(x) + d

  R² Calculation (same as SLR):
    R² = 1 - (SSres / SStot)

  Fit Quality (same thresholds as SLR):
    R² ≥ 0.90 → Excellent, ≥ 0.80 → Very Good, ≥ 0.70 → Good,
    ≥ 0.50 → Moderate, < 0.50 → Weak

  Service Interface (match SLR's pattern):
    analyzeDataset(array $x, array $y): array
      Returns: coefficients, R², equation, fit_quality

    predict(float $monthIndex, float $a, float $b, float $c, float $d): float
    predictUsingAnalysis(array $analysis, float $monthIndex): float

  Dataset Requirements
  --------------------
  • Minimum 4 observations (SLR needs only 2 — polynomial needs more
    data points to fit the curve meaningfully)
  • < 4 observations → fall back to SLR automatically
  • Edge case: nearly-linear data → R² will still be high (polynomial
    is flexible enough to approximate a line)

  MODIFIED: app/Services/AI/AIPredictionService.php
    • Add PolynomialRegressionService as optional dependency
    • Auto-select regression method based on observation count:
      - < 4 obs → SLR (best for minimal data)
      - ≥ 4 obs → Polynomial (better S-curve fit)
    • Add 'regression_method' key to the regression block in the
      Prediction Report: 'slr' or 'polynomial'

  MODIFIED: app/Services/AI/ForecastService.php
    • Accept polynomial coefficients in addition to slope/intercept
    • Use the correct predict method based on regression method

  Testing
  -------
  NEW:  tests/Unit/Services/AI/Regression/PolynomialRegressionServiceTest.php
    • Dataset A — Perfect cubic (x³): verify coefficients exactly
    • Dataset B — S-curve shape (slow start, fast middle, plateau)

  ║ PHASE 3 — Completion Estimation                                         ║
  ╚══════════════════════════════════════════════════════════════════════════╝

   Objective
   ---------
   Estimate when a project will reach 100% cumulative progress and how many
   days it will be delayed. Uses a schedule-aware approach: map current
   actual progress against the planned baseline schedule, compute the
   effective lag, and project completion by shifting the planned end date.

   Prerequisite
   ------------
   Phase 1+2 — Polynomial Regression Engine + Model Selection
   V1 Baseline Schedules (planned_progress_percent)

   Implementation
   -------------
   NEW:  app/Services/AI/CompletionEstimationService.php

   Method (Schedule-Aware):
     • Find effective position on planned schedule:
       Interpolate current_progress against baseline.planned_progress_percent
       to find where the PLAN says this progress level should be
     • Compute lag = currentMonthIndex - effectivePosition
       (positive = behind, negative = ahead)
     • estimated_completion_index = total_planned_months + lag
     • Convert index to date via indexToDate():
       - Within baselines: interpolate between two adjacent baseline dates
       - Past baselines: add extra months to last baseline's date
     • Compute predicted_delay_days = estimated_date - planned_end_date

   Why Schedule-Aware instead of Polynomial/SLR Solve:
     • Polynomial extrapolation far beyond the data range is unreliable
       (accelerating trend → over-optimistic early completion)
     • Schedule-aware ties the estimate to the project's own plan:
       a consistently behind project gets a LATER completion date
     • Polynomial is still used for short-range next-month prediction —
       only the completion estimate (long-range) uses schedule-aware

   Output:
     estimated_completion_index   — Project Month Index at 100%
     estimated_completion_date    — Carbon date
     predicted_delay_days         — positive = delayed, negative = ahead
     completion_confidence        — High / Medium / Low
       • High:   R² ≥ 0.85 AND obs ≥ 6 AND estimated_index ≤ 1.5× planned
       • Medium: R² ≥ 0.70 AND obs ≥ 4
       • Low:    Otherwise (display with strong disclaimer)

   Confidence Rules:
     • If R² < 0.50 → do not estimate (return null)
     • If estimated_index is > 2× the planned end index → Low confidence
     • If obs < 4 → Low confidence

   Integration into Prediction Report:
     AIPredictionService calls CompletionEstimationService after
     the regular pipeline and adds a 'completion' section:
     'completion' => [
       'estimated_completion_index' => ... or null,
       'estimated_completion_date'  => ... or null,
       'predicted_delay_days'       => ... or 0,
       'completion_confidence'      => 'High' | 'Medium' | 'Low' | null,
    ]

  MODIFIED: app/Services/AI/AIPredictionPresenter.php
    • presentNormal(): check completion section in prediction report
    • If completion data exists → populate the previously-deferred
      estimated_completion and predicted_delay_days keys
    • Add completion_confidence to the output

  MODIFIED: resources/views/.../ai-prediction.blade.php

  ║ PHASE 7 — Prediction History / Trend Comparison                          ║
  ╚══════════════════════════════════════════════════════════════════════════╝

  Objective
  ---------
  Save historical predictions so users (and the AI) can see what the
  regression model predicted in previous months versus what actually
  happened. This provides a genuine accuracy signal that replaces
  the misleading use of R² as a "confidence" metric.

  Why R² Is NOT Prediction Confidence
  ------------------------------------
  The current system (and Gemini prompts) treat R² as a confidence
  indicator: "R²: 0.95 — Excellent fit." This is misleading:

    • R² measures how well the curve fits PAST data points.
    • A cubic polynomial can fit 4 points perfectly (R² = 0.999)
      yet predict the 5th month completely wrong (off by 13%).
    • Prediction confidence should be measured by how often
      past predictions matched actual outcomes — which is exactly
      what Prediction History tracks.

  Prediction History provides the REAL confidence metric:
    "In the last 6 months, predictions were Accurate 3 times,
     Close 2 times, Off 1 time."

  Integration with AI (AIExplanationService)
  ------------------------------------------
  Once prediction history data is available, the Gemini prompt in
  AIExplanationService should be updated to include accuracy stats:

    • Replace "R²: 0.95 (Excellent fit)" with:
      "Prediction record: Accurate 3/6, Close 2/6, Off 1/6
      — avg variance: 2.3%"
    • This makes Gemini's analysis text HONEST about the model's
      real-world reliability, not just its curve-fitting ability.
    • The AI can then produce statements like:
      "The model has been consistently overestimating progress
      for the past 3 months — actual results averaged 4% below
      predictions."

  This is a minor prompt update (Step 8) — not a full Phase 10
  AI-powered recommendation change.

  Implementation
  -------------

  ╔══════════════════════════════════════════════════════════════════════════╗
  ║ PHASE 8 — Cross-Project Historical Regression                           ║
  ╚══════════════════════════════════════════════════════════════════════════╝

  Plan file: active_reference/phase8_cross_project_regression_plan.txt

  Objective
  ---------
  Use completed projects of the same category to supplement or replace
  predictions for new projects with insufficient data. Not just a fallback
  for < 2 observations — also supplements projects that have some data
  but not yet a reliable curve.

  Two modes:
    • Fallback (< 2 obs):          aggregate curve replaces "Insufficient Data"
    • Supplementary (< ⅓ planned): prepend synthetic points stabilize regression
    • None (≥ ⅓ planned):          project stands entirely on own data

  Implementation
  -------------
  NEW: app/Services/AI/HistoricalSimilarityService.php

  Method:
    1. Find completed projects matching criteria:
       - Same category
       - Budget within ±20%
       - Duration within ±30%
       - Estimated workers within ±40% (if both sides non-null)
       - Same contractor (bonus weighting)
    2. Normalize each project's progress to percentile timeline (0-100%)
    3. Compute median curve + confidence bands (P25/P75)
    4. Scale aggregate curve to match target project's existing trend
       (handles ahead/behind scenarios)
    5. Generate synthetic points and prepend to real dataset

  Integration with AIPredictionService:
    • shouldSupplement() returns one of: 'fallback' / 'supplement' / 'none'
    • 'fallback': use aggregate as sole dataset → regression on synthetic data
    • 'supplement': prepend synthetic points to reach ⅓ planned months
    • 'none': use existing logic unchanged

================================================================================
  KNOWN DATA GAPS
================================================================================

  Features that need additional data before they become useful:

  • Cross-Project Regression: needs enough completed projects of the
    same category to form meaningful aggregates. Early in system adoption,
    this will return "no similar projects found" — acceptable fallback.
    During development, seed synthetic completed projects for testing.

  • Contractor Performance Tracking: needs projects to be completed.
    Initially all contractors start with neutral/default ratings. Ratings
    become meaningful as projects finish.

  • AI-Powered Recommendations: depends on both contractor performance
    data and issue severity data. Is not useful until Phase 9 is complete
    and there is enough project history.

  • Completion Estimation: polynomial regression makes this viable, but
    very early projects (< 4 obs) will still return null — this is
    correct behaviour.

  • Prediction History: R² has been misused as a confidence metric.
    Prediction History fixes this by tracking actual prediction outcomes.
    However, it needs TIME to accumulate meaningful data — a brand-new
    project with only 1 recorded prediction will show "1 prediction:
    0 Accurate" which is expected behaviour. Accuracy stats become
    meaningful after 3+ prediction cycles.
