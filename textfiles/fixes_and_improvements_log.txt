0. ALLOWED inspection dates 1 month past last scheduled month
----------------------------------------------------------------------
  Branch: fix/progress-date-constraint (from main, independent of Phase 8)
  Files:
    public/js/admin/projects/baseline-schedule-record-progress-modal.js
    public/js/admin/projects/baseline-schedule-edit-progress-modal.js
    resources/views/.../record_monthly_progress_modal.blade.php
    resources/views/.../baseline-schedule.blade.php

  Problem: When a project finishes past its planned end date without
  a formal extension, the progress recording modal blocked inspection
  dates outside the monthly target's calendar month. Users couldn't
  record actual completion (e.g., March 10) against the last scheduled
  target (February).

  Solution: Only the last monthly target allows inspection dates up to
  1 month after the month end. Non-last months keep strict same-month
  constraint to prevent overlapping data. The isLastMonth flag is
  passed via Blade's $loop->last or detected via the dropdown's last
  option.

  How It Works:
  - Last month target:   max = last day of (target month + 1)
  - Non-last month:      max = last day of (target month)

2. FIXED expected_progress reading wrong month's planned value
----------------------------------------------------------------------
  File: app/Services/AI/AIPredictionPresenter.php
  - Root cause: calculateExpectedProgress() filtered baselines by
    planned_date <= now(). When July's planned_date (July 31) hadn't
    arrived yet (July 27), it returned June's 50% instead of July's 56.22%.
  - Meanwhile current_progress already reflected July's actual (52%).
  - Result: progress_gap = -2% (looked ahead) instead of +4.22% (behind).

3. REFINED calculateExpectedProgress with month-aware priority logic
----------------------------------------------------------------------
  File: app/Services/AI/AIPredictionPresenter.php
  - New priority order:
    1. Progress history record for current (simulated) month
    2. Baseline schedule for current (simulated) month
    3. Latest progress history record from any past month
    4. Date-filtered baseline (latest passed)
    5. Time-based estimate
  - Uses DateHelper::now() for the effective current month.

8. CREATED Date Simulation System for dev/testing
----------------------------------------------------------------------
  New Files:
    app/Support/DateHelper.php
    app/Http/Middleware/SimulateDate.php
    app/Http/Controllers/Admin/DevDateController.php

  Modified Files:
    bootstrap/app.php             - registered middleware in web group
    routes/web.php                - dev routes (auth-protected, non-production)
    resources/views/layouts/app.blade.php - floating widget + Ctrl+M hotkey
    app/Services/AI/AIPredictionPresenter.php - now() → DateHelper::now()

  How it works:
    - SimulateDate middleware sets Carbon::setTestNow() from session on request
    - Resets in middleware after-phase (before cookies are created — no logout)
    - DateHelper::now() mirrors the same logic for non-request contexts
    - Ctrl+M toggles floating date picker widget (dev only, APP_ENV != production)
    - Routes: GET /dev/date, POST /dev/date/set, POST /dev/date/clear
    - Global coverage: every now() call respects simulated date
    - Only session/XSRF cookie expiry stays on real time (middleware ordering)

9. FIXED latest progress showing wrong value when multiple inspections exist
----------------------------------------------------------------------
  File: resources/views/.../baseline-schedule.blade.php
  - Before: $plan->progressHistory()->latest('created_at')->first()
  - After:  $plan->progressHistory()->orderBy('inspection_month_date', 'desc')->first()
  - Problem: When a month has two progress records (e.g., Feb 97% and Mar 10 100%),
    sorting by created_at is non-deterministic (same NOW() timestamp), could
    show 97% instead of 100%.
  - Fix: sort by inspection_month_date DESC so the latest inspection wins.
