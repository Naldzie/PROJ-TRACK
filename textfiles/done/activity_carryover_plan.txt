  PLAN FILE
   Activity Carryover — Manual Unfinished Activity Forwarding
   CSPC PMU System
   Last updated: July 18, 2026
================================================================================

================================================================================
  PROBLEM STATEMENT
================================================================================

When a month ends, some baseline checklist activities may remain incomplete
(is_completed = 0). Currently there is no mechanism to move these unfinished
activities to the next month's target. Users must manually re-create the
activity in the new month, losing the connection to the original month's plan.

Simply rewriting baseline_schedule_id and month_label on the activity row
destroys the audit trail — the system would show the activity as if it always
belonged to the new month, erasing the fact that it was NOT completed in its
original target month.

================================================================================
  CHOSEN DIRECTION
================================================================================

Create a project_activity_carryovers log table to record each carryover event
(fully preserving audit history). The activity row itself is updated to point
to the new month, but the complete carryover chain is preserved in the log.

Design decisions:
  - Two trigger modes:
    (a) Prompt after progress recording — after saving monthly progress,
        if activities remain incomplete, show a prompt offering to carry
        each one over to the next chronological month (auto-target).
    (b) Manual button — existing "↗ Carry Over" button on past month
        cards for ad-hoc carryovers (user picks target month via dropdown).
  - Prompt mode auto-selects the next chronological month as the target.
    Manual mode shows a dropdown (user picks).
  - Carryover chain tracked via carryover_number column (1st, 2nd, 3rd...)
  - AI module enhanced with carryover-based recommendation factors
  - is_completed boolean stays as the simple truth on the activity row;
    the carryover log preserves the history of when it was where
  - Multi-month activities handled via naming convention
    (e.g., "Flooring Phase 1", "Flooring Phase 2") — users split the
    work across monthly targets at baseline creation time. A proper
    parent-child hierarchy is overengineering for this system.

    Validation:

      - Target baseline schedule exists, belongs to same project
      - Target month is chronologically AFTER current month

      1. Calculate carryover_number = $activity->carryovers()->count() + 1

         a. Insert ProjectActivityCarryover record

================================================================================
  DESIGN DECISIONS (for reference)
================================================================================

Decision 1 — Carryover triggers
  Two modes: (a) prompt after progress recording, (b) manual button on
  past month cards. Prompt mode auto-targets next chronological month.
  Manual mode requires user to pick target from dropdown.

Decision 2 — Multi-month activities
  Users split long-running activities across monthly targets at baseline
  creation time using naming convention (e.g., "Flooring Phase 1",
  "Flooring Phase 2"). No parent-child hierarchy needed — overengineering
  for this system's scope.

Decision 3 — Audit trail
  project_activity_carryovers table preserves full carryover history.
  The activity row's baseline_schedule_id/month_label gets updated to the
  new target. The original month never falsely claims completion.

Decision 4 — AI integration
  Carryover data feeds RecommendationEngine:
    - carried_over_count (incomplete + carried over) → corrective recs
    - consecutive_carryover (carryover_number >= 2) → escalation recs
