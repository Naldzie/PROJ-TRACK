===============================================================================
  LAZY LOADING — NOT AFFECTED
===============================================================================

The lazy loading is a controller-level pattern, not a service-level one.

  ProjectController::show($id)
    → ProjectDetailService::prepareProjectData($project)
      → returns charts=['ready'=>false], trends=['ready'=>false]   ← no change

  ProjectController::getChartData($id)    (called via AJAX on Progress tab click)
    → ProjectDetailService::prepareChartData()      ← moves to ProjectChartService
    → ProjectDetailService::prepareTrendData()       ← moves to ProjectChartService

After refactoring, the controller calls:
  → ProjectChartService::prepareChartData()   (same inputs, same outputs)
  → ProjectChartService::prepareTrendData()    (same inputs, same outputs)

Zero behavioral change — the AJAX endpoint, the response format, and the
lazy-loading trigger remain identical. Only the internal class changes.

===============================================================================
  DESIGN DECISIONS
===============================================================================

Decision 1 — Pass-through vs direct resolution in controllers
  Context: After extraction, should controllers resolve sub-services directly
  or go through ProjectDetailService?
  Options: (a) Pass-through delegates (safer, fewer controller changes),
  (b) Direct resolution in controllers (cleaner long-term)
  Decision: Start with pass-through delegates. Controllers change only if
  a clear benefit exists (e.g., getChartData() resolving ProjectChartService
  directly since it doesn't need the full orchestrator).
  Rationale: Minimizes regression risk. The pass-through layer is thin and
  can be removed later when all callers are migrated.

Decision 2 — Shared utility methods (formatMonthLabelForDisplay, etc.)
  Context: formatMonthLabelForDisplay(), calculateDaysRemaining(), getStatusColor()
  are used by multiple sub-services.
  Options: (a) Keep in ProjectOverviewService, inject into other services,
  (b) Extract to a shared helper/trait, (c) Duplicate
  Decision: Keep in ProjectOverviewService. Inject ProjectOverviewService
  into ProjectChartService for these methods.
  Rationale: Avoids over-engineering a shared helper for 2-3 small methods.
  The dependency direction is natural (chart service depends on overview).

Decision 3 — Dead V2 code removal
  Context: prepareProjectDataV2() + buildForecastCards() + buildRiskAndActionData()
  are dead code. The V2 button in project_detail.blade.php is commented out.
  Options: (a) Remove all V2 code, (b) Keep for future use
  Decision: Remove. The V2 layout was a prototype that was never activated.
  If needed later, it can be reconstructed from version control.
  Rationale: Dead code creates maintenance burden and confusion.
