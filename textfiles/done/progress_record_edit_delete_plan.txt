================================================================================
  PROBLEM STATEMENT
================================================================================

The backend for editing and deleting progress records is fully implemented
but has no user-facing UI. Three issues exist:

  1. No Edit/Delete buttons exist anywhere in the UI — the Progress Recording
     History table (progress.blade.php) is read-only, and baseline month cards
     have no way to edit recorded progress.

  2. An editProgressModal is referenced by inline JS in project_detail.blade.php
     (openEditProgressModal, saveProgressEdit, deleteProgressRecord) but the
     modal HTML was never built — these functions are dead code.

  3. The existing editProgressRecord() controller method does not handle
     activity completion changes (it stores the audit trail but doesn't sync
     which activities are marked complete for that month).

================================================================================
  DESIGN DECISIONS
================================================================================

Decision 1 — Button visibility pattern
  Context: Codebase uses both @can (policy-based) and direct role checks.
  Decision: Use @can('update', $project) for all edit/delete button visibility.
  Rationale: Editing/deleting progress is logically an "update project" action.
             Reuses the existing ProjectPolicy without creating new methods.
             Staff and admin both can('update') — contractor cannot.
  Consequence: If finer-grained control is ever needed, a dedicated
               can('editProgress') gate can be added later.

Decision 2 — Staff access to history table
  Context: Progress Recording History table is currently admin-only.
  Decision: Open to staff (via @can('update')), but hide "Recorded By" column
            for non-admin roles.
  Rationale: Staff need the table for edit/delete access. Recorded By
             is sensitive — only admin needs to see who recorded what.

Decision 3 — Activities in edit modal
  Context: Record progress modal loads activities via AJAX for the selected
           month; edit modal should do the same.
  Decision: Reuse loadActivitiesForProgressModal() from
            baseline-schedule-record-progress-modal.js.
  Rationale: Avoids duplicating the activity loading logic. The function
             accepts a monthLabel parameter and is already modular.

Decision 4 — Page reload strategy
  Context: Most modals in this codebase reload the page after save to
           reflect changes fully (simplest approach, avoids stale state).
  Decision: Use the same pattern — toast + store activeTab + reload.
  Rationale: Consistent with existing patterns (record progress, add month
             target, carry over). Avoids complex partial-DOM updates that
             could miss edge cases (e.g., audit trail, variance changes).
