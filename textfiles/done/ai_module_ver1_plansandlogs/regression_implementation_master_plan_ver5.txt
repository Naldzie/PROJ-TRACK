SYSTEM OVERVIEW

The system is designed for the Project Management Unit (PMU) to monitor
construction and infrastructure projects.

The PMU is responsible for monitoring project implementation rather than
executing construction work.

Contractors perform the actual construction while the PMU conducts regular
project inspections and monitors progress.

The system digitalizes project monitoring, inspection history, baseline
schedules, activity tracking, documentation, contractor management, and
project reporting.

================================================================================
PROJECT PHILOSOPHY

The AI module is designed as a Decision Support System.

Its purpose is NOT to replace project managers.

Its purpose is NOT to automatically approve or reject project extensions.

Its purpose is to provide project managers with early warning information
derived from historical project progress.

Final decisions always remain with the PMU.



================================================================================
PRIMARY OBJECTIVE OF THE AI MODULE

The AI module does NOT exist simply to predict the next month's percentage.

Prediction is only one component of the overall analytical workflow.

The true objective of the AI module is to answer questions such as:

• Is this project likely to finish on time?

• Is the project currently deviating from its approved schedule?

• Is intervention needed before delays become significant?

• Is the project likely to require an extension?

• What level of schedule risk currently exists?

• What actions should project managers consider?

The regression prediction itself is considered an intermediate analytical
result rather than the final output presented to users.



================================================================================
WHY SIMPLE LINEAR REGRESSION WAS CHOSEN

Construction projects typically follow an S-Curve.

The PMU already prepares planned S-Curves through the Baseline Schedule.

Although S-Curves are nonlinear, the project intentionally uses Simple Linear
Regression for the following reasons:

• Simplicity

• Transparency

• Easy mathematical interpretation

• Suitable scope for undergraduate capstone implementation

• Easy validation

• Easy integration into Laravel

Simple Linear Regression estimates future cumulative ACTUAL progress using
historical inspection records.

The Effective Baseline remains the official planned schedule.

The AI module compares regression forecasts against the Effective Baseline
instead of replacing it.

More advanced regression techniques remain future enhancements.

PROJECT DECISION LOG

The following architectural decisions have been finalized and should not be
changed unless a significant redesign becomes necessary.

Decision 1

Regression predicts only cumulative ACTUAL progress.

Planned progress is always supplied by the Effective Baseline system.



Decision 2

Regression mathematics must remain independent from Laravel models.

LinearRegressionService must never perform database queries.



Decision 3

RegressionDatasetBuilder is responsible only for preparing analytical
datasets.

It does not perform mathematics or business interpretation.



Decision 4

Historical inspection records remain immutable.

Regression may normalize observations internally, but the original project
history must never be modified.



Decision 5

Regression consumes one representative observation per calendar month.

If multiple inspections exist within the same month, only the latest
inspection is used for regression.

Historical reports still display every inspection.



Decision 6

Regression uses the Project Month Index.

Project Month Index replaces calendar month numbers.

Example

January 2026

↓

Project Month Index = 1

February 2026

↓

Project Month Index = 2

...

January 2027

↓

Project Month Index = 13



Decision 7

The AI module is a Decision Support System.

Prediction percentages are intermediate analytical values.

Risk assessment and recommendations are the primary outputs.



Decision 8

ProjectDetailService should remain an orchestrator.

Prediction logic belongs inside AIPredictionService.



Decision 9

Controllers remain thin.

Controllers coordinate services.

Business logic belongs inside Services.



Decision 10

The Effective Baseline always represents the official planned schedule.

Regression forecasts never replace the Effective Baseline.



Decision 11

Historical completed projects are NOT currently merged into the regression
dataset.

Future versions may use historical completed projects for similarity analysis,
validation, or more advanced predictive models.

Decision 12

AIPredictionService is the only public entry point of the AI module.

Other AI services (RegressionDatasetBuilder, LinearRegressionService,
ForecastService, BaselineComparisonService, and
ProjectAssessmentService) are internal implementation services and
should not be called directly by controllers or page services.

This preserves encapsulation and allows future AI enhancements without
changing external callers.

DEVELOPMENT RULES

These rules should be followed throughout the remainder of development.

Rule 1

Always request updated source code before suggesting modifications whenever
there is uncertainty about the current implementation.

Never assume that previously discussed code remains unchanged.



Rule 2

When generating code, always provide complete functions or complete classes.

Avoid partial implementations unless explicitly requested.



Rule 3

Clearly explain:

• where the code belongs

• what it replaces

• what depends on it

• why the modification is necessary



Rule 4

Every generated code block should contain descriptive comments explaining its
purpose whenever practical.



Rule 5

Maintain clean separation of responsibilities.

Regression mathematics

↓

LinearRegressionService

Dataset preparation

↓

RegressionDatasetBuilder

Business interpretation

↓

AIPredictionService

Page orchestration

↓

ProjectDetailService

HTTP handling

↓

Controllers



Rule 6

Avoid introducing unnecessary coupling between services.

Each service should maintain a single primary responsibility.



Rule 7

Prefer expanding existing architecture over redesigning completed components.

The Regression Engine is considered complete and stable.

Future development should build upon it rather than replacing it.



Rule 8

After each implementation step (sub-phase, class, method) is complete, test
it before proceeding to the next step.

Testing ensures each component works correctly in isolation before it becomes
part of a larger integrated workflow.

Test procedures:
• Services: Laravel Tinker or PHPUnit
• Views: Browser verification
• API endpoints: POST/GET request verification
• Fallback scenarios: Verify error handling paths

Do not proceed to the next implementation step until the current step passes
all applicable tests.



Rule 9

Every function and code block must include a descriptive comment label.

Label format depends on complexity:

Simple functions (single responsibility, clear intent):
  • One-line label describing the function's purpose.
  Example:
    // Build and return the regression dataset

Complex functions (multiple steps, business logic, state changes):
  • Purpose explanation — what the function does
  • Caller annotation — what calls this function (if non-obvious)
  • Dependency annotation — what other functions it calls (if non-obvious)
  Example:
    // Orchestrate the full prediction pipeline.
    // Called by: ProjectDetailService::buildAIPredictionData()
    // Calls: buildDataset(), runRegression(), generateForecast(),
    //        compareBaseline(), assessProject()
    // Builds the complete Prediction Report from all AI sub-services.

Non-obvious code blocks (conditionals, loops, error handling):
  • Inline comment explaining why the block exists.
  Example:
    // Clamp prediction to valid range (0-100%)
    // Prevents unrealistic values with sparse datasets

KNOWN LIMITATIONS

The current implementation intentionally has several limitations.

These are accepted because they align with the project's scope.

Current Limitations

Simple Linear Regression assumes an approximately linear trend.

Construction projects generally follow S-Curves.

Regression currently analyzes only one project's historical progress.

External factors are not yet considered.

Examples

Weather

Typhoons

Material shortages

Contractor manpower

Budget changes

Government suspensions

These limitations should be documented during the capstone presentation.



================================================================================
WHY LINEAR REGRESSION IS STILL ACCEPTABLE

Although project progress generally follows an S-Curve, Simple Linear
Regression remains appropriate for the current implementation because:

• It satisfies the predictive analytics requirement.

• It is mathematically transparent.

• Results are easily explainable.

• It is appropriate for undergraduate implementation.

• It forms a solid foundation for future predictive models.

Most importantly,

Regression is only one component of the Decision Support System.

The final recommendation is produced only after business interpretation and
baseline comparison.

══════════════════════════════════════════════════════════════════════════════
1. COMPLETION ESTIMATION
══════════════════════════════════════════════════════════════════════════════

  Problem
  -------
  Version 1 predicts cumulative progress for each remaining baseline month
  but does NOT estimate WHEN the project will reach 100% completion or what
  the final completion percentage will be at the planned end date.

  Proposed Solution
  -----------------
  Solve the regression equation for x (month index) when y = 100%:

    x = (100 − b) / m

  Where:
    m = regression slope
    b = regression intercept

  This gives the estimated month index when cumulative progress reaches
  100%. Compare against the planned completion month to determine delay.

  Outputs
  -------
  • estimated_completion_date  — projected completion date (Carbon)
  • estimated_completion_month — projected Project Month Index at 100%
  • predicted_delay_days       — estimated days beyond planned end date
  • completion_confidence      — derived from R² + remaining months ratio

  Risks
  -----
  • Simple Linear Regression may produce unrealistic long-term estimates
    (especially with limited data). Confidence rating should be prominently
    displayed.
  • The S-Curve nature of construction projects means linear extrapolation
    to 100% is less reliable than short-term forecasts.
  • Recommended minimum: 6+ observations and R² ≥ 0.80 before displaying
    completion estimates.

══════════════════════════════════════════════════════════════════════════════
2. AI-POWERED RECOMMENDATIONS (Phase 7.6)
══════════════════════════════════════════════════════════════════════════════

  Problem
  -------
  Version 1 recommendations are rule-based (if/else). While reliable, they
  lack the nuance and specificity that an AI model could provide.

  Prerequisites
  ------------
  • Issue severity field  — add severity_level (Low/Medium/High/Critical)
    to the issues table to weight open issues in recommendation generation
  • Contractor performance tracking — add performance_rating or
    on_time_delivery_percentage to contractors table
  • Extension reasons — leverage existing extension_reason field from
    project_extensions table to detect recurring delay patterns

  Proposed Solution
  -----------------
  Use Gemini (or an alternative LLM) to generate recommendations based on:
    • Full Prediction Report (regression, forecast, assessment)
    • Open issues with severity context
    • Contractor performance history
    • Previous extension reasons
    • Project type, location, budget utilization

  The AI would generate structured recommendations in the same format as
  the current rule-based output (message, category, reason, priority),
  allowing direct replacement of RecommendationEngine::generate().

  Fallback
  --------
  Keep the rule-based RecommendationEngine as fallback when AI is
  unavailable (same pattern as AIExplanationService).

══════════════════════════════════════════════════════════════════════════════
3. CROSS-PROJECT HISTORICAL REGRESSION
══════════════════════════════════════════════════════════════════════════════

  Problem
  -------
  Each project is analysed in isolation. A newly started project with
  only 1-2 observations cannot use regression at all (insufficient data).

  Proposed Solution
  -----------------
  When a project has insufficient data (< 2 observations), find similar
  COMPLETED projects of the same type/category and use their historical
  progress pattern as a proxy for the new project's expected trajectory.

  Similarity criteria:
    • Same project category/type
    • Similar approved budget range (± 20%)
    • Similar planned duration range (± 30%)
    • Same implementing contractor (bonus weighting)

  Implementation approach:
    • Create HistoricalSimilarityService or extend RegressionDatasetBuilder
    • Normalise similar projects' progress data to a standard timescale
    • Generate an aggregate trend line (mean or median of similar projects)
    • Use this as the regression dataset for new projects
    • Clearly label data as "derived from similar projects" in the UI

  This directly addresses the "Insufficient Data" fallback state and
  provides meaningful predictions even for newly started projects.

══════════════════════════════════════════════════════════════════════════════
4. MULTIPLE LINEAR REGRESSION (MLR)
══════════════════════════════════════════════════════════════════════════════

  Problem
  -------
  Simple Linear Regression uses only ONE independent variable (Project Month
  Index). It cannot account for other factors that influence progress.

  Proposed Independent Variables
  ------------------------------
  • Month Index (existing) — time-based progress
  • Budget Utilization % — how much of the budget has been spent
  • Issue Density — number of open issues per observation period
  • Contractor Experience — number of similar projects completed
  • Seasonality — rainy/dry season indicator (for construction projects)
  • Extension Count — number of previous extensions granted

  Implementation approach:
    • Create MultipleLinearRegressionService in the Regression namespace
    • Use matrix operations (Gaussian elimination or gradient descent)
      instead of the simple Least Squares formula
    • The existing LinearRegressionService remains the default — MLR is
      an alternative for projects with sufficient data depth
    • AIPredictionService can auto-select SLR vs MLR based on available
      data dimensions (or let the user choose via a toggle)

══════════════════════════════════════════════════════════════════════════════
5. FORECAST TABLE / RISK ASSESSMENT TABLE
══════════════════════════════════════════════════════════════════════════════

  Problem
  -------
  Version 1 intentionally omits a month-by-month forecast table because
  Linear Regression predictions show small linear increments (+1-2% per
  month) while actual S-Curve progress shows larger increments (6-9% per
  month). A raw forecast table would be misleading when viewed alongside
  actual S-Curve data.

  Proposed Solution
  -----------------
  Two options for V2:

  Option A — Show forecast table only with strong disclaimers:
    • Requires a toggle/expandable section (hidden by default)
    • Include a "confidence" column showing how far into the future
      the forecast extends (near-term = more reliable)
    • Add a visual S-Curve overlay to contextualise the predictions

  Option B — Replace raw numbers with bandwidth/range forecasts:
    • Instead of "46.33%", show "45-48%" using prediction intervals
    • Wider intervals for later months = more uncertainty
    • More honest representation of linear regression limitations

  Problem

  the regression line or forecast extension.

  Proposed Enhancement

    • Regression line (dashed) — extends from actual data points
    • Forecast extension (dotted) — continues from current month to end

  Technology

  AIPredictionService — no backend changes needed.

══════════════════════════════════════════════════════════════════════════════
8. PREDICTION HISTORY / TREND COMPARISON
══════════════════════════════════════════════════════════════════════════════

  Problem
  -------
  Each prediction is generated from the current snapshot of data. There
  is no record of what the model PREDICTED in previous months versus
  what ACTUALLY happened.

  Proposed Solution
  -----------------
  Save each prediction report to a prediction_history table:

    • project_id
    • generated_at (timestamp)
    • current_progress (at time of prediction)
    • predicted_next_progress (what the model said for next month)
    • actual_next_progress (filled in later when next inspection occurs)
    • regression_snapshot (JSON — full analysis at that point)

  Benefits:
    • Track model accuracy over time
    • Show "Last month we predicted X, actual was Y" in the UI
    • Identify when/why predictions diverge from reality
    • Provide data for model improvement decisions

10. ARCHITECTURAL ENHANCEMENTS
══════════════════════════════════════════════════════════════════════════════

  Caching
  -------
  • Cache prediction results per project (TTL-based, e.g., 1 hour)

  • Reduces DB queries and regression computation for frequently
    viewed projects

  Background Jobs
  ----------------
  • Generate AI analysis via queue job instead of synchronous HTTP call
  • Allows the page to load instantly with stale text while new analysis

  ------------------------
  • Move risk level thresholds (Low/Moderate/High/Critical) to config
    file so PMU staff can adjust without code changes
  • Move fit quality thresholds (Excellent/Very Good/Good/Moderate/Weak)

  • Move recommendation generation rules to config

══════════════════════════════════════════════════════════════════════════════
CURRENT VERSION 1 LIMITATIONS
══════════════════════════════════════════════════════════════════════════════

  These limitations are intentional design decisions for Version 1:

  • No completion date estimation — regression only predicts per-month
    progress, not when 100% will be reached
  • No predicted delay in days — derived from the above
  • No AI-powered recommendations — rule-based only pending more data
  • No forecast table — S-Curve renders linear projections misleading
  • No cross-project analysis — each project analysed independently
  • No prediction history — each prediction is a fresh snapshot
  • No background jobs — AI analysis runs synchronously
  • No prediction caching — each page load re-computes regression
  • Simple Linear Regression only — no multiple variables

CAPSTONE PRESENTATION NOTES

When presenting the AI module, emphasize that:

The regression model is not intended to replace engineering judgement.

The AI module functions as a Decision Support System.

Simple Linear Regression provides statistical forecasting.

The Effective Baseline remains the official project schedule.

The AI compares predicted project behaviour against the Effective Baseline to
identify schedule risks.

Project managers remain responsible for all final decisions.

The architecture intentionally supports future expansion to more advanced
regression techniques and machine learning models without requiring major
system redesign.
