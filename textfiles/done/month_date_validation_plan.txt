================================================================================
  PROBLEM
================================================================================

The Set Up Baseline modal already validates that:
  1) planned_date falls within the month_label's calendar month
  2) New months are added in chronological order
  3) (Partially) Dates respect chronological sequencing

But these same validations are MISSING from the Add Month Target and Edit
flows — both client-side (baseline-schedule-add-month-modal.js) and
server-side (BaselineScheduleController@storeBaselineSchedule,
@updateBaselineSchedule). This means a user can:

  a) Pick month_label = "June" but planned_date = a January date — no
     cross-validation catches it in the Add Month flow.

  b) Add a target chronologically BEFORE an existing target — e.g., add
     a January target after a May target already exists. The only
     enforcement today is progress % ordering, not date ordering.

  c) Add a target with a date BEFORE the project's very first baseline
     start date — e.g., the project starts March 2026, but the user
     adds a January 2026 target.

================================================================================
  CHOSEN DIRECTION
================================================================================

Backport the three validation rules from the Set Up Baseline modal's
addSetupBaselineMonth() + storeInitialBaselineSetup() into every other
add/edit code path. The rules themselves are proven — only the
placement is missing.

The three rules:

  Rule A — "Date must fall within selected month"
    Compare planned_date.substring(0,7) against month_label.
    If mismatch → reject with message.

  Rule B — "New target must be chronologically after all previous targets"
    Compare planned_date against the max planned_date of existing targets.
    If new target <= max existing → reject with message.

  Rule C — "New target must not be before project's baseline start date"
    Compare planned_date against the earliest planned_date in the project.
    If new target < earliest existing → reject with message.

------------------
STEP 1 — Client-side: saveMonthTarget()
------------------

File: public/js/admin/projects/baseline-schedule-add-month-modal.js
Function: saveMonthTarget() (~lines 303-447)

1a. Add Rule A — Date/month consistency

    After line 326 (monthLabel validation) and line 325 (plannedDate validation),
    add a cross-check:

    // Rule A: target date must fall within the selected calendar month
    if (monthLabel && plannedDate) {
        var dateMonth = plannedDate.substring(0, 7);
        if (dateMonth !== monthLabel) {
            errors.push('Target date must fall within ' +
                formatMonthLabel(monthLabel) + '.');
        }
    }

    (Format: use the same formatMonthLabel() that already exists in the setup
     modal's JS. The add-month JS file doesn't have it — either import the
     utility function or inline a simpler helper.)

1b. Add Rule B — Chronological ordering

    After the progress % checks (~line 361), add:

    // Rule B: new target must be chronologically after all existing targets
    var existingDates = [];
    document.querySelectorAll(
        '#sCurvePlanTableBody > div[style*="background: white"]'
    ).forEach(function (card) {
        // Extract month_label from the card's badge text
        var monthBadge = card.querySelector('span[style*="background: #dbeafe"]');
        if (monthBadge) {
            var match = monthBadge.textContent.match(/\d{4}-\d{2}/);
            if (match) existingDates.push(match[0]);
        }
    });
    if (existingDates.length > 0) {
        existingDates.sort();
        var latest = existingDates[existingDates.length - 1];
        if (monthLabel && monthLabel <= latest) {
            errors.push('"' + formatMonthLabel(monthLabel) +
                '" must be chronologically after all previously added months ' +
                '(latest: "' + formatMonthLabel(latest) + '"). ' +
                'Add months in chronological order.');
        }
    }

1c. Add Rule C — Before-start guard

    // Rule C: new target must not be before the project's first baseline target
    if (existingDates.length > 0) {
        existingDates.sort();
        var earliest = existingDates[0];
        if (monthLabel && monthLabel < earliest) {
            errors.push('"' + formatMonthLabel(monthLabel) +
                '" cannot be earlier than the project\'s first baseline target ' +
                '(' + formatMonthLabel(earliest) + ').');
        }
    }

    NOTE: The same DOM query used for Rule B can be reused for Rule C — just
    read existingDates[0] instead of the last element. Consider extracting
    the query loop to a shared helper to avoid duplication.

------------------
STEP 2 — Client-side: saveMonthTargetEdit()
------------------

File: public/js/admin/projects/baseline-schedule-add-month-modal.js
Function: saveMonthTargetEdit() (~lines 454-519)

The edit flow is simpler because the month_label is LOCKED (readonly during
edit — see line 175: monthInput.disabled = true). So:

  Rule A — Not needed in edit mode. The month cannot change, and the date
           was already validated when the row was first created. The user
           can edit the date but the month stays the same → if they pick a
           date outside the month, Rule A should still apply since they
           could manually type a different date.

  Rule B — Not applicable during edit. The row already exists in the
           sequence; only its progress % and date within the same month
           can change.

  Rule C — Not needed (same reasoning as B).

Therefore: only add Rule A to saveMonthTargetEdit(), to catch cases where
the user types a planned_date that doesn't match the locked month_label.

    // Rule A: edited date must still fall within the month
    var editMonth = document.getElementById('monthLabel').value;  // locked
    if (editMonth && plannedDate) {
        var dateMonth = plannedDate.substring(0, 7);
        if (dateMonth !== editMonth) {
            errors.push('Target date must fall within ' +
                formatMonthLabel(editMonth) + '.');
        }
    }

STEP 3 — Server-side: storeBaselineSchedule()
------------------

File: app/Http/Controllers/BaselineScheduleController.php
Method: storeBaselineSchedule() (~lines 70-204)

3a. Rule A — Date/month consistency

    After the existing duplicate-month check (~line 93), add:

    // Rule A: target date must fall within the selected calendar month
    $dateMonth = substr($validated['planned_date'], 0, 7);
    if ($dateMonth !== $validated['month_label']) {
        return response()->json([
            'success' => false,
            'message' => 'Target date must fall within ' . $validated['month_label']
        ], 422);
    }

3b. Rule B — Chronological ordering

    Before the existing progress validation block (~line 99), determine the
    latest existing planned_date:

    // Rule B: new target must be chronologically after existing targets
    $latestDate = ProjectBaselineSchedule::where('project_id', $project->id)
        ->max('planned_date');
    if ($latestDate && $validated['planned_date'] <= $latestDate) {
        return response()->json([
            'success' => false,
            'message' => 'New target must be chronologically after the latest existing target (' . $latestDate . ').'
        ], 422);
    }

3c. Rule C — Before-start guard

    // Rule C: new target must not be before the project's first baseline date
    $earliestDate = ProjectBaselineSchedule::where('project_id', $project->id)
        ->min('planned_date');
    if ($earliestDate && $validated['planned_date'] < $earliestDate) {
        return response()->json([
            'success' => false,
            'message' => 'Target date cannot be before the project\'s first baseline target (' . $earliestDate . ').'
        ], 422);
    }

    PLACEMENT NOTE: If $latestDate and $earliestDate are both queried, they
    can be combined into a single DB query to the same table. Consider:

        $dateRange = ProjectBaselineSchedule::where('project_id', $project->id)
            ->selectRaw('MIN(planned_date) as earliest, MAX(planned_date) as latest')
            ->first();

    Then check $dateRange->latest and $dateRange->earliest. Reduces 2 queries
    to 1.

================================================================================
  DESIGN DECISIONS
================================================================================

Decision 1 — Server-side is authoritative; client-side is for UX
  All three rules are enforced on the SERVER (controller) as the single
  source of truth. The client-side checks in JS exist only to give the user
  immediate feedback without a round-trip. If there is any discrepancy, the
  server's response wins.

Decision 2 — Edit flow only needs Rule A
  During edit, the month_label is locked (readonly/disabled). The user
  cannot change which month the row belongs to. Rule B (ordering) is not
  needed because the row's position in the sequence doesn't change. Only
  Rule A matters — to prevent the user from picking a planned_date that
  falls outside the row's month.

Decision 3 — Rules A, B, C apply to both pre-extension and post-extension
  These are not extension-aware rules. They enforce valid data structure
  regardless of extension_count. The extension-awareness for progress %
  validation (B6) is separate and already implemented.

Decision 4 — Earliest-date reference (Rule C)
  For Rule C, the "project's baseline start" is defined as the earliest
  planned_date across ALL baseline schedule rows for the project. This is
  the simplest and most consistent definition — it doesn't require knowing
  the project's official start date from a separate field.
