================================================================================
  1. PROBLEM STATEMENT
================================================================================

  Current State
  -------------
  The system generates predictions every time ProjectDetailService loads
  the AI Prediction tab. These predictions are computed and displayed,
  but NEVER saved for later comparison. Once the next month's actual
  progress is recorded, the previous prediction is lost forever.

  The system currently uses R² as a proxy for "prediction confidence":
    "R²: 0.95 (Excellent fit)" — shown in the UI and sent to Gemini.

  This is mathematically incorrect:
    • R² measures how well the regression curve fits PAST data points.
    • A degree-3 polynomial can fit 4 points with R² = 0.999 yet the
      5th prediction can be off by 10+ percent.
    • R² says nothing about whether the NEXT prediction will be accurate.

  What Is Missing
  ---------------
  1. No record of what was predicted in previous months
  2. No comparison between predicted vs actual progress
  3. No way to calculate real prediction accuracy over time
  4. Gemini's analysis text uses R² as "confidence" — misleading

  What This Phase Builds
  ----------------------
  A prediction_history table that captures every prediction at generation
  time, then back-fills actual_next when new progress is recorded. The
  presenter exposes historical accuracy data, the Blade shows it in a
  color-coded table, and Gemini's prompt is updated to use actual
  accuracy stats instead of raw R².

================================================================================
  2. CHOSEN DIRECTION
================================================================================

  Decision 1 — Append-Only History
    Each prediction creates a new row. The actual_next column starts
    NULL and is filled later when the corresponding progress is recorded.
    No records are ever modified or deleted (immutability).

  Decision 2 — Dedup by current_progress
    When a page reload triggers generatePrediction() again with the
    same current_progress, the duplicate save is skipped. This prevents
    flood from F5 refreshes while still allowing real updates when new
    progress is recorded.

  Decision 3 — Accuracy Badges
    Three tiers based on |predicted - actual|:
      • Accurate: variance < 2%
      • Close:    variance < 5%
      • Off:      variance >= 5%

  Decision 4 — Gemini Prompt Enhancement
    Instead of "R²: 0.95 (Excellent fit)", the prompt should include:
      "Prediction accuracy (last N months):
       Accurate X, Close Y, Off Z — avg variance: W%"
    This replaces a misleading metric with an honest one.

  New private method:

    private function savePredictionHistory(
        Project $project,
        array $analysis,
        float $currentProgress,
        float $predictedNextProgress,
        int $currentMonthIndex
    ): void {
        // Skip for insufficient data or completed projects
        if ($currentProgress >= 100) return;

        // Skip duplicate: same project + same current_progress
        $exists = PredictionHistory::where('project_id', $project->id)
            ->where('current_progress', $currentProgress)
            ->exists();
        if ($exists) return;

        // Fetch month_label for the PREDICTED month (not current month)
        // offset($currentMonthIndex) vs offset($currentMonthIndex - 1)
        $monthLabel = ProjectBaselineSchedule::where('project_id', $project->id)
            ->orderBy('planned_date')
            ->offset($currentMonthIndex)
            ->limit(1)
            ->value('month_label');

        // Fallback: predicted month may be beyond the last baseline schedule
        if (!$monthLabel) {
            $last = ProjectBaselineSchedule::where('project_id', $project->id)
                ->orderBy('planned_date', 'desc')
                ->first(['month_label']);
            if ($last) {
                $monthLabel = Carbon::parse($last->month_label . '-01')
                    ->addMonth()->format('Y-m');
            }
        }

        PredictionHistory::create([
            'project_id'          => $project->id,
            'month_label'         => $monthLabel,
            'regression_method'   => $analysis['regression_method'] ?? 'slr',
            'current_progress'    => round($currentProgress, 2),
            'predicted_next'      => round($predictedNextProgress, 2),
            'r_squared'           => $analysis['r_squared'] ?? 0,
            'regression_snapshot' => $analysis,
        ]);
    }

  Edge Cases:
    • < 2 observations → skip (minimal report, no analysis)
    • current_progress >= 100 → skip (project complete)
    • Duplicate current_progress → skip (page reload guard)
    • No baseline schedule for predicted month → fallback calculates
      next month label from last schedule + 1 month
    • Throws on DB failure → caught by existing try/catch in caller

    // Check if there's a pending prediction to update
    try {
        $pending = PredictionHistory::where('project_id', $project->id)
            ->whereNull('actual_next')
            ->latest('created_at')
            ->first();

        if ($pending) {
            $pending->actual_next = $actualProgressPercent;
            $pending->save();
        }
    } catch (\Exception $e) {
        // Non-blocking — prediction history update failure should
        // not prevent the progress record from being created
        Log::warning('Failed to update prediction history', [
            'project_id' => $project->id,
            'error' => $e->getMessage(),
        ]);
    }

  Edge Cases:
    • No pending prediction → skip gracefully
    • DB write fails → caught by try/catch, progress record still saved
    • Multiple pending predictions → only latest is updated (oldest
      stays NULL — acceptable, we only track the most recent cycle)

===============================================================================
   POST-IMPLEMENTATION FIXES
===============================================================================

  FIX 1 � month_label column (added via second migration)
  ------
  Discovered during testing: the Month column in the history table showed
  created_at (the date the prediction was MADE) instead of the target
  month (the month the prediction was FOR).
  
  Solution:
    � New migration 2026_07_26_000001_add_month_label_to_prediction_history.php
      adds a VARCHAR(10) month_label column
    � Presenter displays month_label parsed as 'M Y' (e.g. "Jan 2026")
      via Carbon::parse(->month_label . '-01')->format('M Y')
    � Falls back to created_at->format('M Y') for records without month_label

  FIX 2 � month_label offset bug (points to predicted month, not current)
  ------
  savePredictionHistory() used offset( - 1) which
  fetched the CURRENT month's baseline schedule. But predicted_next is
  for the NEXT month, so the month_label should be the predicted month.
  
  Solution: Changed to offset(). If no baseline
  exists at that position (prediction beyond last schedule), fallback
  calculates next month_label from the last schedule + 1 month.

  FIX 3 � Risk status uses current gap + near-term forecast (not far-future)
  ------
  The status (ON TRACK / AT RISK) was determined by the LAST assessment
  record (furthest forecast month). A project could be -8% behind now
  but show "ON TRACK" because the model predicted it would catch up
  months in the future.
  
  Additionally, Moderate risk (-10% to 0% variance) mapped to "ON TRACK",
  but being up to 10% behind schedule is a genuine concern.
  
  Solution (AIPredictionPresenter.php):
    � Now combines two signals: current progress gap (actual vs planned)
      and near-term assessment (first forecast month)
    � Picks the more conservative (higher risk) of the two
    � Only 'Low' risk maps to ON TRACK; 'Moderate', 'High', 'Critical'
      all map to AT RISK
