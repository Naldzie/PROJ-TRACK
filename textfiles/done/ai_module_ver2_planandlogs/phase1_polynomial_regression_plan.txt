  2. PROBLEM STATEMENT
================================================================================

  Current State:
    The V1 module uses Simple Linear Regression (SLR) to predict cumulative
    progress. SLR assumes a linear relationship: y = mx + b.

  Problem:
    Construction projects follow an S-Curve (slow start → rapid middle →
    plateauing completion). SLR draws a straight line through this curved
    data, producing systematic errors:
      • Overestimates early progress (actual is below the line)
      • Underestimates mid-project progress (actual is above the line)
      • Overestimates late progress (actual plateaus, line keeps rising)

    This makes SLR predictions unreliable for:
      • Completion date estimation
      • Forecast tables (month-by-month predictions show linear increments)
      • S-Curve chart overlays (a straight line over an S-curve is misleading)
      • Confidence in predictions (users can see the line doesn't fit)

  Evidence from V1 testing:
    Dataset "Very Good" fit (R² ≈ 0.89) uses saturating data:
      x = [1, 2, 3, 4, 5, 6, 7, 8]
      y = [2, 5, 10, 16, 19, 20, 21, 21]
    SLR: slope ≈ 2.93, intercept ≈ 1.07, R² ≈ 0.89
    Notice: actual progress flattens at months 6-8, but SLR predicts
    continued linear growth. A polynomial would capture this plateau.


================================================================================
  3. CHOSEN DIRECTION
================================================================================

  Decision: Implement Polynomial Regression (degree 3 / cubic)
    Equation: y = ax³ + bx² + cx + d

  Why Degree 3:
    • A cubic polynomial bends twice — matching S-curve shape
      (slow start → rapid growth → plateau)
    • Still solved via Least Squares (same mathematical family as SLR)
    • Still transparent — coefficients a, b, c, d have intuitive meaning
    • Does not require external libraries — pure PHP math
    • Complements rather than replaces SLR

  What It Is NOT:
    • NOT a neural network or ML model
    • NOT a black box — the equation is still explainable
    • NOT a replacement for SLR — both will coexist

  Architecture Decision:
    PolynomialRegressionService is a NEW class alongside
    LinearRegressionService. Both share the same public interface so
    AIPredictionService can call either one interchangeably.

  ==============================================================================
  STEP 1 — Create PolynomialRegressionService
  ==============================================================================

  File:   app/Services/AI/Regression/PolynomialRegressionService.php
  Status: ⬜ NOT STARTED

  Purpose
  -------
  Perform polynomial (cubic) regression on a dataset using the Least Squares
  method via Gaussian Elimination.

  This class follows the EXACT same pattern as LinearRegressionService:
    • Same namespace (App\Services\AI\Regression)
    • Same public method names (analyzeDataset, predict, predictUsingAnalysis)
    • Same return array keys (with additional coefficient keys)
    • Same fit quality classification
    • Zero Laravel dependencies — pure PHP math

  Dependencies
  ------------
  None — this is a standalone math class.

  Public Interface
  ----------------
    analyzeDataset(array $x, array $y): array
      Returns: observation_count, coefficients [a, b, c, d],
               equation, r_squared, fit_quality

    predict(float $monthIndex, float $a, float $b, float $c, float $d): float
      Returns: Predicted cumulative progress at the given month index

    predictUsingAnalysis(array $analysis, float $monthIndex): float
      Convenience wrapper — extracts coefficients from analysis array

  Mathematical Method — Least Squares via Gaussian Elimination
  -----------------------------------------------------------

  Step 1 — Set up the normal equations for cubic regression:

    We want to find coefficients a, b, c, d that minimize the sum of
    squared errors for y = ax³ + bx² + cx + d.

    The normal equations are:

    [ Σx⁶   Σx⁵   Σx⁴   Σx³ ] [ a ]   [ Σx³y ]
    [ Σx⁵   Σx⁴   Σx³   Σx² ] [ b ] = [ Σx²y ]
    [ Σx⁴   Σx³   Σx²   Σx  ] [ c ]   [ Σxy  ]
    [ Σx³   Σx²   Σx    n   ] [ d ]   [ Σy   ]

    Where:
      Σx⁶   = sum of x^6 for each data point
      Σx³y  = sum of (x^3 * y) for each data point
      n     = number of observations

  Step 2 — Build the 4×4 matrix and 4×1 right-hand side vector:

    private function buildNormalEquations(array $x, array $y): array
      // Called by: analyzeDataset()
      // Builds the augmented matrix [A | b] for the 4×4 system

    For each data point (xi, yi):
      x2 = xi²,  x3 = xi³,  x4 = xi⁴,  x5 = xi⁵,  x6 = xi⁶
      row 0: [x6, x5, x4, x3 | x3*yi]
      row 1: [x5, x4, x3, x2 | x2*yi]
      row 2: [x4, x3, x2, xi | xi*yi]
      row 3: [x3, x2, xi,  1 | yi]

  Step 3 — Solve using Gaussian Elimination with Partial Pivoting:

    Forward Elimination:
      For each column k (0 to 3):
        1. Find pivot: row with largest absolute value in column k
        2. Swap current row with pivot row
        3. If pivot is near-zero → the system is singular (throw exception)
        4. For each row below pivot:
           factor = A[row][k] / A[pivot][k]
           Subtract factor × pivot row from this row

    Back Substitution:
      For each row from bottom to top:
        solution[row] = (b[row] - Σ(A[row][col] × solution[col])) / A[row][row]

    Returns: [a, b, c, d] coefficients

  Step 4 — Calculate R²:

    R² = 1 - (SSres / SStot)

    Where:
      SSres = Σ(yi - y_predicted_i)²
      SStot = Σ(yi - y_mean)²

    Same formula as SLR — measures how well the polynomial fits the data.

  Step 5 — Classify Fit Quality:

    Same thresholds as SLR (from LinearRegressionService):
      R² ≥ 0.90  → Excellent
      R² ≥ 0.80  → Very Good
      R² ≥ 0.70  → Good
      R² ≥ 0.50  → Moderate
      R² < 0.50  → Weak

  Step 6 — Format Equation:

    Examples:
      "y = 0.0500x³ - 1.2000x² + 10.5000x - 5.0000"
      "y = -0.0200x³ + 0.8000x² + 2.0000x + 1.0000"

  Validation Rules
  ----------------
    • X and Y must have the same count → InvalidArgumentException
    • Fewer than 4 observations → InvalidArgumentException
      (cubic needs at least 4 points to determine 4 coefficients)
    • Identical X values → RuntimeException
    • Singular matrix → RuntimeException

  Return Array Structure
  ----------------------
  [
      'observation_count' => int,
      'coefficients' => [a, b, c, d],       // NEW — polynomial-specific
      'a' => float,  // x³ coefficient
      'b' => float,  // x² coefficient
      'c' => float,  // x coefficient
      'd' => float,  // intercept
      'equation' => 'y = ax³ + bx² + cx + d',
      'r_squared' => float,
      'fit_quality' => 'Excellent|Very Good|Good|Moderate|Weak',
  ]

  ==============================================================================
  STEP 5 — Add 'regression_method' to Prediction Report
  ==============================================================================

  The Prediction Report already has a 'regression' section with keys:
    observation_count, mean_x, mean_y, slope, intercept,
    equation, r_squared, fit_quality

  For polynomial, the 'regression' section will contain:
    observation_count, coefficients [a,b,c,d]
    equation (polynomial format), r_squared, fit_quality
    regression_method: 'polynomial'
    method_reason: string

  For SLR, the 'regression' section gets one new key:
    regression_method: 'slr'
    method_reason: string

  The existing keys (slope, intercept, mean_x, mean_y) remain present
  for SLR. For polynomial, additional coefficient keys (a, b, c, d,
  coefficients) are added alongside the standard keys.

  This is fully backward compatible:
    • V1 blades that read 'equation', 'r_squared', 'fit_quality' still work
    • New blades can read 'regression_method' to show model info
    • No existing code breaks

  9. DECISION LOG
================================================================================

  Decision 1 — Polynomial vs Other Methods
    Context: Multiple options exist for improving regression accuracy
    Options considered: Polynomial (deg 3), Logistic (sigmoid), MLR, ARIMA
    Decision: Polynomial Regression (degree 3)
    Rationale:
      • Same Least Squares math family as SLR — transparent and verifiable
      • Degree 3 bends twice, matching S-curve shape
      • Pure PHP — no external libraries needed
      • Fits naturally alongside existing LinearRegressionService

  Decision 2 — Separate Class vs Extending SLR
    Context: Should polynomial logic go inside LinearRegressionService
            or be a separate class?
    Options: New class, or add method to existing class
    Decision: New PolynomialRegressionService class
    Rationale:
      • Single Responsibility — each regression model is its own class
      • No risk of breaking existing SLR code
      • Clean interface — both classes share same method names
      • Follows the existing pattern (DatasetBuilder is also a standalone class)

  Decision 3 — Model Selection Logic
    Context: Should the user choose SLR vs Polynomial, or should the system?
    Options: User toggle, auto-select, or both
    Decision: Auto-select with R² comparison
    Rationale:
      • PMU users should not need to understand regression models
      • If polynomial fits significantly better, use it
      • If both are similar, prefer SLR (simpler, more stable)
      • Always fall back to SLR when data is insufficient (< 4 obs)

  Decision 4 — Minimum Observations for Polynomial
    Context: Cubic regression needs at least 4 data points
    Options: 4 (absolute minimum) or higher
    Decision: 4 observations minimum
    Rationale:
      • Mathematically required (4 coefficients to determine)
      • With < 4 observations, SLR is the correct fallback
      • The model selection logic handles this automatically

  Decision 5 — When to Add Polynomial to the Dataset Builder
    Context: Does RegressionDatasetBuilder need changes for polynomial?
    Decision: No changes needed
    Rationale:
      • DatasetBuilder only prepares X/Y arrays — same format for any model
      • Polynomial and SLR consume the same dataset
      • The math difference is only in how coefficients are computed
