===============================================================================
  1. OBJECTIVE
===============================================================================

  Instead of showing only one completion estimate, the system should provide
  three independent completion estimation methods simultaneously so project
  managers can compare different forecasting approaches.

  This strengthens the system as a Decision Support System (DSS) — PMU users
  see a range of possibilities rather than a single number, and the agreement
  or disagreement between methods conveys additional decision-making context.


===============================================================================
  2. THE THREE METHODS
===============================================================================

  2.1 Polynomial Regression (Newton-Raphson) — NEW
  -------------------------------------------------------------------------------
  Trend-based prediction using the existing cubic polynomial equation.

  Method: Solve ax³ + bx² + cx + (d - 100) = 0 via Newton-Raphson

    f(x)   = ax³ + bx² + cx + (d - 100)
    f'(x)  = 3ax² + 2bx + c
    x₀     = total_planned_months + 1  (initial guess)
    x_{n+1}= x_n - f(x_n) / f'(x_n)
    Max iterations: 100
    Tolerance: 0.0001

  Guards:
    • R² < 0.50 → return null (unreliable regression)
    • regression_method !== 'polynomial' → return null
    • Solver fails to converge → return null

  Interpretation: "What the polynomial curve says — assumes current
  acceleration/deceleration trends continue."


  2.2 Schedule-Aware (Constant Lag) — KEEP EXISTING
  -------------------------------------------------------------------------------
  Conservative lag-based projection. NO CHANGES.

  Formula (existing):
    ES = Effective Position (interpolated on baseline curve)
    Lag = AT - ES
    Estimated Index = PD + Lag

  Interpretation: "You are X months behind the plan, so completion shifts
  by X months — assumes future work at planned rate."


  2.3 Earned Schedule EAC_time (Standard ES) — NEW
  -------------------------------------------------------------------------------
  Standard Earned Value Management Earned Schedule formula.

  Formula:
    ES   = Effective Position (same interpolation as schedule-aware)
    AT   = Current Month Index
    SPI(t) = ES / AT
    IEAC(t) = PD / SPI(t) = PD × AT / ES
    (when SPI(t) > 0; if ≤ 0 → return null)

  Guard: No baselines → null (cannot compute ES)

  Interpretation: "Your efficiency ratio (ES/AT) stays constant going forward
  — assumes current pace continues."

  Key mathematical difference from Schedule-Aware:
    ┌──────────────────┬────────────────────┬───────────────────────────┐
    │ Scenario         │ Schedule-Aware     │ Earned Schedule EAC_time │
    │                  │ (PD + Lag)         │ (PD / SPI(t))            │
    ├──────────────────┼────────────────────┼───────────────────────────┤
    │ Behind (ES < AT) │ PD + (AT - ES)     │ PD × AT / ES (more lag)  │
    │ Ahead  (ES > AT) │ PD - (ES - AT)     │ PD × AT / ES (less lag)  │
    │ On time (ES = AT)│ PD                 │ PD                       │
    └──────────────────┴────────────────────┴───────────────────────────┘

  The Earned Schedule method is MORE CONSERVATIVE when behind because it
  compounds the efficiency loss across the remaining duration, rather than
  assuming the remaining work proceeds at the planned rate.


===============================================================================
  3. CONFIDENCE CLASSIFICATION (shared logic)
===============================================================================

  All three methods share the same confidence classification rules:

    High:   R² ≥ 0.85 AND obs ≥ 6 AND index ≤ 1.5 × planned
    Medium: R² ≥ 0.70 AND obs ≥ 4
    Low:    Otherwise
    Null:   R² < 0.50 (no estimate at all)

  For Polynomial method: uses the polynomial R²
  For Schedule-Aware: uses the regression R² (same as current)
  For Earned Schedule: uses the regression R² (same as current)


===============================================================================
  4. COMPARISON SUMMARY
===============================================================================

  Fields:
    • earliest_date  — Carbon or null (earliest of the three valid estimates)
    • latest_date    — Carbon or null (latest of the three valid estimates)
    • spread_days    — int (latest - earliest in days, 0 if < 2 estimates)
    • agreement      — string (based on spread_days)
    • valid_count    — int (how many methods returned a value)

  Agreement classification:
    High:     spread_days ≤ 15  — all methods converging
    Moderate: spread_days ≤ 45  — some divergence
    Low:      spread_days > 45  — methods disagree significantly
    N/A:      valid_count < 2   — insufficient estimates to compare

  If only 1 method returns a value, agreement = 'N/A' and spread = 0.
  If 0 methods return a value, all fields are null / 0 / 'N/A'.

  5.1 New Service: CompletionComparisonService
  -------------------------------------------------------------------------------
  File:   app/Services/AI/CompletionComparisonService.php
  Status: ✅ COMPLETE

  Responsibilities:
    • Run all 3 completion estimation methods
    • Normalize results into identical structure per method
    • Compute comparison summary (earliest/latest/spread/agreement)

  Public Interface:
    estimateAll(
        Carbon $plannedEndDate,
        array  $analysis,           // regression block
        int    $currentMonthIndex,
        float  $currentProgress,
        Collection $baselineSchedules
    ): array

  Return Structure:
    [
        'methods' => [
            'polynomial' => [
                'estimated_completion_index' => float|null,
                'estimated_completion_date'  => Carbon|null,
                'predicted_delay_days'       => int|null,
                'completion_confidence'      => string|null,
                'label'      => 'Polynomial (Trend-Based)',
                'label_short' => 'Polynomial',
            ],
            'schedule_aware' => [
                'estimated_completion_index' => float|null,
                'estimated_completion_date'  => Carbon|null,
                'predicted_delay_days'       => int|null,
                'completion_confidence'      => string|null,
                'label'      => 'Schedule-Aware (Conservative)',
                'label_short' => 'Schedule-Aware',
            ],
            'earned_schedule' => [
                'estimated_completion_index' => float|null,
                'estimated_completion_date'  => Carbon|null,
                'predicted_delay_days'       => int|null,
                'completion_confidence'      => string|null,
                'label'      => 'Earned Schedule EAC_time',
                'label_short' => 'EAC_time',
            ],
        ],
        'comparison' => [
            'earliest_date' => Carbon|null,
            'latest_date'   => Carbon|null,
            'spread_days'   => int,
            'agreement'     => 'High'|'Moderate'|'Low'|'N/A',
            'valid_count'   => int,
        ],
    ]

  Internal flow:
    1. Call $completionEstimationService->estimate() for schedule-aware (existing)
    2. Call $this->estimatePolynomial() for polynomial solve (new)
    3. Call $this->estimateEarnedSchedule() for EAC_time (new)
    4. Compute comparison from the 3 results
    5. Return combined array


  5.2 Modified: CompletionEstimationService
  -------------------------------------------------------------------------------
  File:   app/Services/AI/CompletionEstimationService.php
  Status: ✅ COMPLETE

  Add new public method:
    estimatePolynomial(
        array $analysis,
        int   $totalPlannedMonths,
        Carbon $plannedEndDate
    ): ?array

  Implementation (Newton-Raphson cubic solver):
    • Extract coefficients a, b, c, d from $analysis
    • Guard: regression_method !== 'polynomial' → null
    • Guard: r_squared < 0.50 → null
    • Define f(x) = ax³ + bx² + cx + (d - 100)
    • Define f'(x) = 3ax² + 2bx + c
    • Initial guess x₀ = max($totalPlannedMonths + 1, $currentMonthIndex + 1)
    • Iterate: x_{n+1} = x_n - f(x_n) / f'(x_n)
    • Max 100 iterations, tolerance 0.0001
    • If |f(x)| < tolerance → converged
    • Clamp result: must be > current month index
    • Convert to date using existing indexToDate() or baseline interpolation
    • Classify confidence using existing classifyConfidence()

  Add new public method:
    estimateEarnedSchedule(
        Carbon $plannedEndDate,
        int    $currentMonthIndex,
        float  $currentProgress,
        Collection $baselineSchedules
    ): ?array

  Implementation:
    • Compute ES via findEffectivePosition() (same as schedule-aware)
    • Guard: ES === null → return null
    • Guard: AT ≤ 0 or ES ≤ 0 → return null
    • SPI(t) = ES / AT
    • Guard: SPI(t) ≤ 0 → return null
    • IEAC_index = PD / SPI(t) = PD × AT / ES
    • Guard: IEAC_index ≤ currentMonthIndex → return null (already done)
    • Convert to date using existing indexToDate()
    • Compute delay = estimated_date - planned_end_date
    • Classify confidence using existing classifyConfidence()
    • Return same structure as estimate()

===============================================================================
  10. DECISION LOG
===============================================================================

  Decision 1 — Separate Service vs Extending CompletionEstimationService
    Context: Should the polynomial and ES methods go into the existing
             CompletionEstimationService or a new service?
    Options: New CompletionComparisonService, or add to existing
    Decision: New CompletionComparisonService for orchestration; individual
              solver methods added to CompletionEstimationService
    Rationale:
      • CompletionEstimationService already has indexToDate() and
        classifyConfidence() helpers — reusing them avoids duplication
      • CompletionComparisonService is a new responsibility (orchestration
        + comparison) that doesn't belong in the estimation service
      • Clean separation: estimation math in CompletionEstimationService,
        multi-method orchestration in CompletionComparisonService

  Decision 2 — Backward Compatibility
    Context: The blade and presenter both read single 'completion' keys
    Decision: Keep existing 'completion' key unchanged. Add new
              'completion_multi' key alongside it.
    Rationale:
      • Zero risk of breaking existing blades
      • The old timeline card continues working with single-keys
      • The new multi-method card reads from completion_multi
      • Both coexist until the old card is optionally removed later

  Decision 3 — Polynomial Solver Location
    Context: Newton-Raphson was removed in v1.1 (over-optimistic)
    Decision: Re-implement and label clearly as "Trend-Based (Best-Case)"
    Rationale:
      • Labeling it as "best-case" sets correct expectations
      • Displaying alongside conservative methods shows the range
      • PMU managers see the full picture, not just one number
      • The polynomial estimate is informative even if over-optimistic

  Decision 4 — Earned Schedule Formula Variance
    Context: Which IEAC formula to use
    Options: IEAC(t) = PD / SPI(t) (standard), or IEAC(t) = AT + (PD - ES)/SPI(t)
    Decision: IEAC(t) = PD / SPI(t) = PD × AT / ES (standard long form)
    Rationale:
      • This is the most widely cited ES formula in EVM literature
      • Mathematically equivalent to AT + (PD - ES) / SPI(t)
      • More conservative than schedule-aware when behind (different assumptions)
      • Clearly distinct from the existing method, providing genuine comparison value
