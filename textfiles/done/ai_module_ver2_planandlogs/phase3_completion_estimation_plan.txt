   Objective
   ---------
   Estimate when a project will reach 100% cumulative progress using a
   schedule-aware approach: map current actual progress against the planned
   schedule (baselines), compute the lag (behind/ahead), and project the
   completion date by shifting the planned end by that lag.

   • Phase 2 — Model selection stores coefficients [a,b,c,d] in regression
     block; method_reason and r_squared_slr/r_squared_poly available
   • V1 — Baseline schedules with planned_progress_percent values

================================================================================
  COMPLETION ESTIMATION SERVICE — DESIGN
================================================================================

  Class:        App\Services\AI\CompletionEstimationService
  Constructor:  Project $project, array $analysis (regression block),
                int $currentMonthIndex, Collection $baselineSchedules
  Method:       estimate(): array|null

   Algorithm (Schedule-Aware)
   ---------
   1. If current_progress >= 100 → return null (already complete)
   2. If regression R² < 0.50 → return null (unreliable fit)
   3. Find effective position on planned schedule:
      - Interpolate current_progress against baselineSchedules[*].planned_progress_percent
      - Returns the fractional month index where the PLAN says this progress should be
      - e.g., 42% between baseline 8 (40%) and baseline 9 (50%) → effective = 8.2
      - If progress ≤ first baseline → effective = 1.0
      - If progress ≥ last baseline → effective = total_planned_months
   4. Compute lag = currentMonthIndex - effectivePosition
      - Positive lag = behind schedule; Negative lag = ahead of schedule
   5. Estimated completion index = total_planned_months + lag
   6. Validate estimated index:
      - Must be > currentMonthIndex
      - If <= currentMonthIndex → return null (effectively already done)
      - If > MAX_REASONABLE_MONTHS (1000) → return null
   7. Convert month index to date via indexToDate():
      - If floor(index) < schedules->count():
        - Interpolate between baseline at floor(index)-1 and next baseline
        - partial month interpolation via fraction * days_in_month
      - Else (past all baselines):
        - Add extra months to last baseline's date
        - Add fraction * 30 days
   8. Compute predicted_delay_days:
      estimated_date - project->planned_end_date (Carbon diff in days)
   9. Determine confidence (same rules, uses regression R²):
      - If R² < 0.50 → null (already filtered)
      - High:   R² ≥ 0.85 AND obs ≥ 6 AND estimated_index ≤ 1.5 × planned_index
      - Medium: R² ≥ 0.70 AND obs ≥ 4
      - Low:    otherwise
      - If estimated_index > 2 × planned_index → downgrade to Low
      - If obs < 4 → Low

   Key Design Rationale
   --------------------
   • Polynomial regression is used for SHORT-RANGE next-month prediction
     (captures acceleration in recent data)
   • Schedule-aware method is used for LONG-RANGE completion estimation
     (conservative, tied to the project's own plan)
   • This prevents the polynomial from extrapolating unrealistically:
     a project consistently behind schedule will NOT get an over-optimistic
     early completion date
   • The regression R² is still used for confidence classification since it
     reflects overall data quality

   Return structure:
     [
       'estimated_completion_index' => float,
       'estimated_completion_date'  => Carbon,
       'predicted_delay_days'       => int,
       'completion_confidence'      => 'High'|'Medium'|'Low'|null,
     ]

   Edge Cases
   ----------
   • Already ≥ 100% progress → null
   • R² < 0.50 → null
   • No baseline schedules → null (cannot compute effective position)
   • Empty baseline collection → null
   • Progress below first planned value → effective = 1.0 (assume start)
   • Progress past last planned value → effective = total_months
   • Estimated index <= current month → null (completion already passed)
   • Estimated index extremely large (> 1000 months) → null

================================================================================
   NOTES
   ================================================================================

   • Schedule-aware approach chosen over Newton-Raphson cubic solving because:
     - Polynomial extrapolation far beyond the data range is unreliable
       (accelerating trend → over-optimistic completion dates)
     - Schedule-aware ties the estimate to the project's own plan:
       consistently behind projects get later completion dates
     - Uses existing baselineSchedules.planned_progress_percent data
     - No complex root-finding needed (simple interpolation)
   • Polynomial regression is still used for NEXT-MONTH prediction and
     the short-range forecast — only the COMPLETION ESTIMATE uses
     schedule-aware logic
   • All completion estimation is additive — V1 code unchanged
   • Blade already has the Estimated Completion slot hardcoded as
     "Not enough data" — this is the first time it will render real data
   • If CompletionEstimationService throws or returns null, the presenter
     simply shows "Not enough data" as before (graceful degradation)
